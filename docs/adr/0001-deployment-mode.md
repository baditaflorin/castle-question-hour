# 0001 — Deployment mode: C (Pages frontend + Docker backend)

- Status: accepted
- Date: 2026-05-11

## Context

The product is a castle-wide ritual: hourly anonymous reflection prompts that surface as themes
at meal time. The technology pieces named in the brief are **Yjs over a WebRTC mesh, a local LLM,
and Piper**. The brief explicitly wants:

1. Hourly pushes to every phone in the castle.
2. Anonymous local aggregation of answers.
3. A spoken summary at meal time, generated by a local LLM and rendered by Piper.

Modes available:

- **A — pure GitHub Pages**: would require everything (signaling, scheduler, LLM, TTS) to run in
  the browser. WebLLM and a WASM Piper exist, but:
  - Web Push notifications fired on an hourly cadence with one phone "missing" must be triggered
    *somewhere* — browsers won't reliably fire push from a peer; PushManager requires a server
    with VAPID keys.
  - A WebRTC mesh still needs a signaling rendezvous. There is no static-only way to do this
    without a third-party broker (which contradicts the "local-first, no cloud" intent).
  - Running an LLM on a phone for the meal summary is unreliable enough to fail the success
    metric "3–7 coherent themes in <60s".
- **B — Pages + pre-built data**: the data here is not pre-buildable; it's user-generated at
  runtime.
- **C — Pages frontend + Docker backend**: a single small box inside the castle network can host
  the signaling server, the hourly cron, the push sender, an Ollama instance, and Piper. Phones
  load the static frontend from Pages (so we get free TLS + CDN for the UI) and connect to the
  castle's local backend for the runtime parts.

## Decision

**Mode C.** The frontend ships to GitHub Pages. The backend ships as a Docker image to GHCR and
runs on a single Linux box inside the castle (laptop, NUC, Raspberry Pi 5, whatever). Public host
port `25342` behind nginx, per §17 constraints.

## Consequences

- §3 (ADRs), §4 (Go backend), §8 (containerization), §9 (deploy), §10 (nginx) all apply in full.
- The Pages frontend is configurable at build time so different castles can point at different
  backend URLs without redeploying Pages.
- We accept the operational cost: the castle steward must run `docker compose up -d` on a local
  box. This is documented in [deploy/README.md](../../deploy/README.md).
- Backend secrets (VAPID keys, optional Ollama API URL) stay on the box, never in git, never in
  the frontend bundle.

## Alternatives considered

- Hosting the backend on a public VPS: ruled out because the brief is local-first and answers
  should not leave the castle network.
- A serverless function for the hourly push: still requires VAPID keys on a server, still
  requires WebRTC signaling, still doesn't run Piper — a strictly worse Mode C.
